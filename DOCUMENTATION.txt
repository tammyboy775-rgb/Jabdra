1. INTRODUCTION
================================================================================

1.1 PURPOSE OF THIS DOCUMENT
  This document defines the functional, non-functional, and technical aspects of
  the FreshFind Website as built, and records its compliance with the FreshFind
  Software Requirements Specification (SRS) Version 1.0. It describes the
  objectives and features of the Website, its pages and the functions it
  performs, the data it uses, the constraints under which it operates,
  installation instructions, test data, and assumptions.

1.2 BACKGROUND AND NECESSITY FOR THE WEBSITE
  Farmers markets connect communities with the growers who put fresh, seasonal
  food on their tables. However, information on market locations and timings is
  scattered across flyers, community boards, social media, and word of mouth,
  with no single reliable source for residents in a community or neighbourhood.
  This makes it difficult for residents to plan visits around a market's actual
  operating day and hours, or to know in advance what produce is likely to be
  available that week. There is a clear requirement for a simple, accessible,
  browser-based tool that consolidates this information into one place, helping
  residents discover nearby markets and make the most of seasonal, local
  produce.

1.3 PROPOSED SOLUTION
  FreshFind is a Single Page Application (Website) that helps residents discover
  nearby farmers markets. It displays market locations, operating days and
  hours, and the types of produce typically available at each market. It
  includes an AI chatbot that answers frequently asked queries from visitors.
  The Website is built purely with frontend technologies (HTML, CSS,
  JavaScript/React) with no backend server. All market and produce data is
  presented from pre-populated JSON/JavaScript data files, and the chatbot runs
  on pre-scripted, rule-based logic rather than a live external AI service.
  This architecture keeps the platform lightweight, fast, and easy to deploy
  while providing a responsive experience across desktops, tablets, and mobile
  devices.

1.4 SCOPE OF THE PROJECT
  FreshFind is a responsive, browser-based Website that helps residents discover
  farmers' markets near them and plan visits around what is likely to be in
  season. It includes:
    - A searchable and filterable market directory.
    - Individual market detail pages showing location, operating days/hours,
      and typical products.
    - A general produce guide and a seasonal recommendations section.
    - An AI (scripted) chatbot to help visitors find answers to common queries.
    - A content bookmarking system (favourites, notes, export, sharing).
    - Responsive compatibility across desktops, tablets, and mobile devices.
  The platform is suitable for residents planning market visits and for
  community organizations promoting local farmers.

1.5 INTENDED AUDIENCE
  Stakeholders (technical and non-technical people associated with the project)
  and the developers of this Website. It serves as a reference for both
  stakeholders and developers involved in designing, building, and maintaining
  the Website.

2. SYSTEM OVERVIEW
================================================================================

2.1 ARCHITECTURE
  FreshFind is a client-side Single Page Application (SPA). There is no backend
  server and no database. Data is read from static files bundled at build time;
  nothing is ever written to a server. User choices that must survive a page
  reload (bookmarks, notes, session) are kept in the browser's localStorage
  only, which satisfies the SRS constraint that the Website must not store
  information on a server.

  High-level architecture:

  +-----------------------------------------------------------------------+
  |                        BROWSER (Client)                               |
  |                                                                       |
  |  +------------------- React SPA (Vite build) -----------------------+ |
  |  |  Pages: Home, Directory, Market Detail, Produce Guide, Seasonal, | |
  |  |         Bookmarks, Contact, About, Login, Register               | |
  |  |  Shared: Navbar, Footer, Chatbot, Breadcrumbs, Search/Filter     | |
  |  |  State:  MarketsContext, BookmarksContext, AuthContext           | |
  |  +-------------------------------------------------------------------+ |
  |           |  read-only            |  read               |             |
  |           v                       v                     v             |
  |  marketData.json / marketData.js   messages.json    localStorage       |
  |  (markets, produce, seasons)       (chatbot Q&A)    (bookmarks,        |
  |                                                      notes, session)   |
  |           |                                                     ^      |
  |           v                                                     |      |
  |  Geolocation API + real-time clock -> "Open now" / distance      |      |
  |  Google Maps embed (market detail page)                          |      |
  +-----------------------------------------------------------------------+
           |
           v
   Optional external view-only links: Google Maps tiles, social share URLs
   (WhatsApp, X, Facebook). Static hosting: any web server / CDN.

  Data flow for a typical request:
    1. User opens the Home page (or any route).
    2. MarketsContext loads the bundled market dataset (marketData.json).
    3. A page filters/sorts the data in memory (search, day, product, open-now,
       proximity via Geolocation API) and renders the result.
    4. Selecting a market routes to the Market Detail page (SPA navigation,
       no full page reload; ScrollToTop resets the viewport).
    5. Chatbot input is matched against messages.json (rule-based) and the
       answer is displayed; no network call to an AI service occurs.

3. FEATURE DOCUMENTATION (FUNCTIONAL REQUIREMENTS)
================================================================================

  The portal is a responsive Website with a set of pages and menus that
  represent the choice of activities to be performed. Pages, menus, and other
  visual elements are designed in a visually appealing manner with attractive
  fonts, colors, and animations, laid out responsively. Information is
  retrieved from pre-populated JSON/JS data files and displayed through React
  components, modules, and the Context API (the SRS hint: "Use ... ReactJS
  components, modules, and other features to implement this").

3.1 HOME PAGE (route: /)
  Source: src/pages/Home/Home.jsx, src/components/Hero/Hero.jsx
  SRS items covered:
    - Display elements: platform logo (Navbar brand), heading, and
      introductory text (Hero headline and sub-copy).
    - Quick Find: a prominent "Find a Market Near You" search prompt in the
      Hero that accepts a market/neighborhood query and deep-links into the
      directory (/directory?q=...). Quick-link chips jump to "Open Saturdays"
      (/directory?day=Sat), the Produce Guide, and "What's in season".
    - Highlights: a featured showcase of markets ("Featured this week" - first
      three market cards) and a rotating hero image carousel (5 slides,
      auto-advances every 6 seconds, pauses when the tab is hidden, honors
      prefers-reduced-motion, manual dot controls).
    - Seasonal picks panel showing what is in season right now (computed from
      the current date).
    - "How it works" three-step explainer (search nearby, check schedule,
      shop in season).
    - Chatbot Launcher: the floating chatbot icon is available on the home
      page and all subsequent pages (rendered globally by the router).
  Dynamic behavior: selecting a market or applying a filter navigates to the
  directory/detail pages where results are displayed dynamically.

3.2 MARKET DIRECTORY - FIND A MARKET (route: /directory)
  Source: src/pages/Directory/Directory.jsx, src/components/SearchFilter/,
          src/components/MarketCard/, src/components/LiveMarketStatus/
  SRS items covered:
    - Functionality: displays a catalog of farmers markets loaded from the
      pre-populated market data file (marketData.json via MarketsContext -
      31 markets across 22 Lagos neighborhoods).
    - Each market card includes: market name, area/neighborhood, operating
      days and hours, a short description, and product thumbnails (product
      images with icon fallback), plus vendor count and an "Open now" badge
      computed from the live clock.
    - Filtering: by area/neighborhood (free-text search over name and
      neighborhood), day of the week (day chips Mon-Sun), produce type
      available (category dropdown), and an "Open now" status toggle.
    - Sorting: alphabetically (A-Z), by proximity (nearest first, using
      browser Geolocation + haversine distance; gracefully falls back to
      alphabetical with a visible notice when location is unavailable), and
      by next open day.
    - Result count, contextual sort/status notes, empty-state messaging.
    - URL parameter support (?q=, ?day=) so hero search/quick links land on
      pre-filtered results.
    - "Use my location" retry button when geolocation is denied/unavailable.
    - Breadcrumb navigation; LiveMarketStatus bar (open-now count, real-time
      clock, simulated visitor counter, geolocation status).

3.3 MARKET DETAIL PAGE (route: /market/:id)
  Source: src/pages/MarketDetail/MarketDetail.jsx
  SRS items covered:
    - Location details: full address, area/neighborhood badge, and an
      embedded Google Map showing the market location (iframe embed built
      from the market's coordinates).
    - Schedule: operating days and hours clearly displayed in the "Visit
      info" panel (open days list + hours range); the card grid also shows
      days/hours at a glance.
    - Products available: a list/grid of items typically available at this
      market with images/icons ("Typical products" tiles).
    - Additional: "About this market" description, distance from the user
      (when geolocation is granted), bookmark toggle, back-link to the
      directory, loading/error/not-found states.

3.4 PRODUCE GUIDE (route: /produce-guide)
  Source: src/pages/ProduceGuide/ProduceGuide.jsx, data in marketData.js
  SRS items covered:
    - Functionality: a browsable catalogue of produce types, each with a
      description/usage tip, the months it is typically in season (12-month
      season bar), and search.
    - Filtering: text search over produce names; the list is constrained to
      produce actually carried by markets in the directory (data linkage
      between produce items and markets). Product category browsing is also
      available in the directory's "Sells" filter (fruits, vegetables, herbs,
      dairy, etc. - 14 categories).
    - Data source: loaded from pre-populated data (produceGuide entries with
      season windows) linking produce to seasons; market-level linkage comes
      from each market's product list.
    - Bookmarks: each produce entry has a bookmark button.

3.5 SEASONAL RECOMMENDATIONS (route: /seasonal)
  Source: src/pages/Seasonal/Seasonal.jsx, src/components/SeasonalPicks/
  SRS: "seasonal recommendations section" (Scope of Project).
    - Four season cards (spring/summer/autumn/winter) with blurbs and picks.
    - The current season (derived from the device date) is highlighted with a
      "Happening now" tag; a CTA links to the directory.
    - Home page shows the "In season right now" picks panel.


3.6 AI CHATBOT (floating widget, available on every page)
  Source: src/components/Chatbot/Chatbot.jsx, data in messages.json
  SRS items covered:
    - Functionality: a floating chatbot widget available across the site that
      helps visitors find answers to common queries. A FAB (floating action
      button) opens/closes the chat panel on any page.
    - Data source: responses are generated from a static, pre-scripted
      dataset - 63 Q&A entries with 367 trigger phrases in messages.json.
      Matching normalizes the user's text (lowercase, punctuation stripped)
      and looks for a matching known question. NO live external AI service or
      backend is used (per SRS constraint).
    - Interaction: visitors can type a question or select from suggested
      quick-reply prompts (five quick messages, collapsible); the chatbot
      responds with text answers, a fallback message for unknown questions,
      and can link to relevant market pages (nearby-market results render as
      clickable cards that open the market detail route).
    - Special capability: "nearest market" intents trigger browser
      geolocation, compute great-circle distances to all markets, and return
      the three closest markets with distances; permission-denied and
      unsupported-browser cases return friendly messages. A loading spinner
      is shown while locating.

3.7 CONTENT BOOKMARKING SYSTEM (route: /bookmarks)
  Source: src/context/BookmarksContext.jsx, src/components/BookmarkButton/,
          src/pages/Bookmarks/Bookmarks.jsx
  SRS: "For all content types, the following should be available:"
    - Favorite markets and produce guide entries: bookmark toggle buttons on
      market cards, the market detail page, and every produce guide row
      (two bookmark kinds: market, produce). The Navbar shows a bookmark
      icon with a live count.
    - Personal notes attached to bookmarked content: a note textarea on each
      bookmark card (stored client-side in localStorage; not sent anywhere).
    - Export bookmarks as a formatted list: "Copy list" (clipboard) and
      "Print list" (browser print) produce a structured plain-text export
      grouped by MARKETS and PRODUCE including notes; a preview box shows
      the formatted output.
    - Share recommendations via social links: share buttons for WhatsApp,
      X (Twitter), and Facebook that pre-fill the pick list and site URL.
    - Management: remove bookmark, empty state with CTA, direct links back to
      each bookmarked item.
  Note: SRS says notes are "session-only"; implementation persists them in
  localStorage (client-only), which is a superset of the requirement and
  still stores nothing on a server.


3.8 CONTACT US (route: /contact)
  Source: src/pages/Contact/Contact.jsx
  SRS: "This page includes static contact information, with a map showing

    - FAQ section ("Before you write") with expandable questions.
    - Google Maps / geolocation: the geolocation feature is used

3.9 ABOUT US (route: /about)
  Source: src/pages/About/About.jsx
  SRS: "This page includes static information about the team and the

    - Intro section, "Our platform" story section, and a three-member team

    - Breadcrumb navigation included.

3.10 LOGIN / SIGN UP (routes: /login, /register)
  Source: src/components/AuthForm/AuthForm.jsx, src/context/AuthContext.jsx
  SRS: "Dummy Login/Signup: Non-functional login/signup buttons included for
  design continuity."
    - The SRS minimum is non-functional buttons for design continuity. This
      implementation provides the same look/flow plus a lightweight
      client-side demo auth: registration and login validate input, keep the
      "account" list and current session in localStorage only, show the
      username with a Log out action in the Navbar, and guard against
      duplicate usernames. It is NOT real authentication - no server, no
      password hashing, no data leaves the browser - so it fully complies
      with the no-backend constraint while exceeding the dummy requirement.

3.11 USER INTERFACE FEATURES
  Source: LiveMarketStatus, Navbar, Breadcrumb, Hero, index.html, CSS files
  SRS items covered:
    - Visitor Counter: simulated visitor counter using JavaScript
      (LiveMarketStatus shows "N visitors today" that drifts over time from
      a randomized base).
    - Real-Time Clock: a live clock (updates every second, weekday + time)
      plus browser geolocation usage to highlight markets open "right now"
      where applicable (open-now badge on cards, "N open right now" in the
      status bar, "Open now" filter in the directory).
    - Hover Effects: hover effects and animated transitions throughout
      (cards, buttons, links), route fade-in transitions, and hero reveal
      animations; all motion honors the prefers-reduced-motion setting.
    - Breadcrumb Navigation: breadcrumbs on the Directory and About pages
      (Home / current); market detail uses an explicit "Back to all markets"
      link.
    - Dummy Login/Signup: see 3.10.
    - Responsive layout: mobile navigation drawer, fluid grids, and
      breakpoint-based styling for desktops, tablets, and mobiles.
    - SEO/accessibility basics: semantic landmarks, aria labels/roles,
      alt text, meta description, Open Graph and Twitter card tags; Google
      Lighthouse is the recommended validation tool (see section 9).

  These instructions are mandatory per the SRS deliverables list.

8.1 PREREQUISITES
    - Node.js 18.x or newer (LTS recommended) with npm.
      Check:   node --version  /  npm --version
    - A modern browser (Chrome, Edge, Firefox, or Safari).
    - (Optional) Git, to clone the repository.
    - (Optional) Visual Studio Code as the editor.

8.2 INSTALLATION (development)
    1. Obtain the source code (unzip the submitted archive, or clone the
       repository).
    2. Open a terminal in the project root folder (the folder containing
       package.json).
    3. Install dependencies:
          npm install
    4. Start the development server:
          npm run dev
    5. Open the printed local URL (default: http://localhost:5173) in a
       browser. The app is fully client-side; no other services are needed.

8.3 PRODUCTION BUILD
    1. Build the optimized static site:
          npm run build
       Output is written to the dist/ folder.
    2. Preview the production build locally:
          npm run preview
       (default: http://localhost:4173)

8.4 LINT (code quality check)
          npm run lint

8.5 DEPLOYMENT (optional live URL)
    Upload the contents of dist/ to any static host (GitHub Pages, Netlify,
    Vercel, Firebase Hosting, or any web server). Because the app uses
    client-side routing, configure the host to serve index.html for unknown
    paths (SPA fallback / "rewrite all to index.html").

10. ASSUMPTIONS
================================================================================

  A-01  All market, produce, and chatbot content is demonstration data.
        Market records cover Lagos neighborhoods; the bundled reference
        datasets also contain a fictional "Millhaven" example set. Swapping
        in real data requires only editing the JSON/JS data files - no code
        changes - which matches the SRS model of pre-populated data files.
  A-02  Hours are stored as a single daily range (e.g. "6:00 AM - 6:00 PM")
        applied to every listed open day; markets with different weekend
        hours would need separate records.
  A-03  The login/signup feature is a design-continuity demo (client-side
        only). It is not secure authentication and must not be treated as
        real user accounts; passwords are stored in plain text in
        localStorage. The SRS only required dummy buttons.
  A-04  Bookmarks, notes, and session data persist per browser/device
        (localStorage). Clearing browser storage removes them. Nothing is
        synced across devices (there is no backend, per SRS).
  A-05  The visitor counter is simulated (randomized) exactly as the SRS
        asks; it is not backed by analytics.
  A-06  The contact form validates and confirms locally but does not send
        email; there is no server to receive it (SRS constraint).
  A-07  Geolocation features (proximity sort, distances, chatbot nearby
        markets) require user permission and HTTPS/localhost; graceful
        fallbacks apply otherwise.
  A-08  Google Maps embeds and social share links are optional, view-only
        external resources; the site remains usable without them.
  A-09  "Open now" calculations use the visitor device's local time and the
        market's stored weekday names/hours.
  A-10  Browser support targets the latest versions of Chrome, Edge,
        Firefox, and Safari (SRS: "compatible with the latest browsers").

11. KNOWN ISSUES AND LIMITATIONS
================================================================================

  These are the [PARTIAL] items from the compliance matrix, plus advisory
  notes. None of them violate the SRS constraints; each is a candidate for
  a small enhancement.

  K-01  Contact page map: the SRS hints at a map with live location on the
        Contact Us page. An embedded Google Map is implemented on every
        Market Detail page, and geolocation is used across the site, but the
        Contact page currently shows static contact details without its own
        map embed. (Requirement: PARTIAL)

  K-02  Produce guide category filter: the SRS suggests filtering the
        produce guide by product category (fruits, vegetables, herbs, dairy,
        ...). The guide currently offers text search, while category
        filtering is available in the Market Directory's "Sells" dropdown.
        Adding category chips to the guide would close this gap.
        (Requirement: PARTIAL)

  K-03  Lint warnings: oxlint reports 5 advisory warnings (0 errors) -
        setState-in-effect patterns in useGeolocation/MarketsContext and
        fast-refresh export style in the context files. They do not affect
        functionality.

  K-04  Two market datasets exist: the directory/chatbot load
        marketData.json (31 Lagos markets - the active dataset), while
        marketData.js also carries the original demo markets plus the
        produce/season reference data. Consolidating into one file would
        reduce confusion.

  K-05  Auth is intentionally demo-grade (see assumption A-03).

  K-06  Hero images are large photos (~1.5-1.8 MB each); converting them to
        WebP/AVIF and adding responsive sizes would improve Lighthouse
        performance scores.
